# Журнал решений

Короткие записи о важных решениях: что решили, почему и что из этого следует. Новые записи добавляются в конец, старые не переписываются. Если решение меняется, добавляется новая запись со ссылкой на старую.

## 001. API внутри Next.js

**Дата:** 2026-10-31
**Статус:** принято

**Решение:** API (ТЗ §8) делается на Next.js route handlers в том же проекте, что и сайт.

**Почему:** один проект, один деплой и один язык (TypeScript) для сайта и API. На объёмах MVP отдельный сервис не нужен.

**Последствия:** код доступа к базе держим в отдельном модуле, чтобы при росте нагрузки API можно было вынести в отдельный сервис без переписывания страниц.

## 002. MVP без бюджета

**Дата:** 2026-10-31
**Статус:** принято

**Решение:** MVP запускается только на бесплатных тарифах: сайт на Vercel по адресу `maqala.vercel.app`, база на Supabase (до 500 МБ), код и CI на GitHub. Домен maqala.kz покупается после MVP.

**Почему:** бюджета на домен и хостинг нет. Бесплатно зарегистрировать домен .kz нельзя, а по правилам зоны .kz сайт должен размещаться на серверах в Казахстане.

**Последствия:**
- в продакшен-базе сначала только статьи Казахстана, чтобы уложиться в 500 МБ;
- проверка скорости поиска на 1 млн записей делается локально;
- при покупке домена .kz отдельно решается, где размещать сайт.

## 003. Единственный источник в MVP: OpenAlex

**Дата:** 2026-10-31
**Статус:** принято

**Решение:** в MVP данные берутся только из OpenAlex. CORE, Crossref и казахстанские репозитории подключаются после MVP.

**Почему:** OpenAlex закрывает основную массу метаданных, страны авторов и темы, у него открытый API. Один источник позволяет быстрее дойти до работающего продукта.

**Последствия:** коннектор изолирован, чтобы следующие источники добавлялись рядом без изменения сайта.

## 004. Храним только метаданные

**Дата:** 2026-10-31
**Статус:** принято

**Решение:** храним только метаданные и ссылки на оригинал. Полные тексты и PDF не копируем.

**Почему:** юридические требования (ТЗ §10) и экономия места в бесплатной базе.

## 005. Авторы хранятся в jsonb внутри статьи

**Дата:** 2026-11-01
**Статус:** принято

**Решение:** авторы и их организации лежат в колонке `works.authors` (`jsonb`), отдельных таблиц авторов и организаций в MVP нет.

**Почему:** в MVP авторы нужны только для показа в карточке и на странице статьи (FR-4, FR-5). Поиска и страниц по авторам нет, а таблицы связей усложнили бы загрузку.

**Последствия:** если понадобятся страницы авторов или организаций, их вынесут в отдельные таблицы миграцией. Страны авторов уже вынесены в `works.countries` (массив с GIN-индексом) для фильтров.

## 006. Размер базы и бесплатный лимит Supabase

**Дата:** 2026-11-01
**Статус:** открыто, решить на этапе 5

**Факт:** 2000 статей занимают 29 МБ, из них 16 МБ — исходная запись `raw`. Все открытые статьи Казахстана (~109 тысяч) займут около 1,6 ГБ, а бесплатный Supabase даёт 500 МБ.

**Варианты:** не хранить `raw` в продакшене (оставить только локально), обрезать список авторов в `raw`, загружать в продакшен только часть статей (например, за последние годы).

**Последствия:** до этапа 5 храним всё; перед деплоем выбрать вариант и записать сюда.

## 007. Поиск на конфигурации `simple`

**Дата:** 2026-11-01
**Статус:** принято

**Решение:** полнотекстовый поиск — PostgreSQL `tsvector` с конфигурацией `simple`: название с весом A, аннотация с весом B, запрос через `websearch_to_tsquery` (кавычки для фраз, `-слово` для исключения).

**Почему:** одна конфигурация одинаково работает для русского, казахского и английского. Языковые словари PostgreSQL есть для русского и английского, но не для казахского, а метка языка в данных ненадёжна (см. `docs/data-sources.md`).

**Последствия:** морфология не учитывается: «нефть» не найдёт «нефти». Улучшение — после MVP: словари, триграммы (`pg_trgm`) или Meilisearch (ТЗ §13).

## 008. Язык статьи определяется по тексту

**Дата:** 2026-11-03
**Статус:** принято

**Решение:** коннектор уточняет язык по **названию** (аннотация учитывается, только если в названии меньше 15 букв). Есть буква казахского алфавита (ә, ғ, қ, ң, ө, ұ, ү, һ; одна «і» — только если источник не указал украинский или белорусский) — казахский; кириллицы больше латиницы — русский (если источник не указал другой кириллический язык); текст на латинице с меткой `ru` или `kk` — английский. В остальных случаях остаётся метка источника. Исходная метка сохраняется в `raw`.

Сначала учитывалась и аннотация, но казахстанские журналы часто дают аннотацию сразу на казахском, русском и английском, и русские статьи становились «казахскими». После смены правил язык пересчитывается без запросов к API: `python -m ingest.openalex.relabel_languages`.

**Почему:** метка языка OpenAlex часто ошибается (см. `docs/data-sources.md`), а для проекта важно отличать казахские статьи от русских.

**Последствия:** фильтр «Язык» на сайте становится точнее для казахского и русского. Поиск по аннотации по-прежнему находит русские статьи с казахской частью аннотации: чтобы видеть только казахские, нужен фильтр «Язык».

## 009. Три языка интерфейса через префикс в адресе

**Дата:** 2026-11-05
**Статус:** принято (меняет пункт ТЗ §5 «в MVP один язык»)

**Решение:** интерфейс сразу на русском, казахском и английском. Язык — первая часть адреса: `/ru/...`, `/kk/...`, `/en/...`. Адрес без префикса перенаправляется (`web/middleware.ts`) на язык из cookie, затем из настроек браузера, иначе на русский. Строки интерфейса лежат в словарях `web/lib/i18n/{ru,kk,en}.ts`; русский — образец, остальные проверяются по его типу. Названия стран и языков, числа и даты форматируются через `Intl` для выбранного языка.

**Почему:** аудитория — Казахстан и СНГ, а для поиска и SEO нужна отдельная страница на каждом языке (ТЗ §5, hreflang).

**Последствия:** новый текст в интерфейсе добавляется во все три словаря, иначе проект не соберётся. Названия областей науки пока приходят из OpenAlex на английском. Казахский перевод стоит проверить носителю языка.

## 010. Аккаунты, роли и админка

**Дата:** 2026-11-05
**Статус:** принято (меняет ТЗ §3: регистрация и личные кабинеты входят в MVP)

**Решение:**
- Вход по почте и паролю и через Google (OAuth 2.0 + PKCE, ключи в `.env`). Своя реализация на стандартных средствах Node.js, без библиотек авторизации.
- Пароли — scrypt (N = 2^15) с солью. Сессия — случайный токен в cookie `httpOnly`, `SameSite=Lax`; в базе только SHA-256 токена, срок 30 дней.
- Роли: `user`, `editor` (правит, скрывает и добавляет статьи), `superadmin` (плюс пользователи, загрузки, журнал). Первого суперадмина назначают командой `npm run set-role -- почта superadmin`; через сайт роль себе не выдать.
- Права проверяются на сервере в каждой странице и каждом действии; админка для остальных отвечает 404.
- Все действия админки пишутся в `audit_log`.
- Исправленная в админке статья помечается `edited_at`, и коннектор её больше не перезаписывает. Скрытая (`is_hidden`) не видна нигде на сайте.
- Загрузку из админки ставят в очередь `ingest_jobs`, выполняет `python -m ingest.worker` (локально его может запускать сайт при `INGEST_AUTORUN=1`).

**Почему:** нужны избранное и личные настройки, а запросы на удаление записей (ТЗ §10) и ошибки в данных должен кто-то обрабатывать через интерфейс, а не через базу.

**Последствия:**
- Почта при регистрации с паролем пока не подтверждается (нет сервиса отправки писем). Поэтому роли по почте не выдаются, а при входе через Google в аккаунт с той же неподтверждённой почтой пароль сбрасывается, чтобы чужая регистрация не сохранила доступ.
- Нет восстановления пароля по почте — добавить вместе с отправкой писем.
- Хранятся персональные данные (имя, почта): нужна политика конфиденциальности перед запуском.
